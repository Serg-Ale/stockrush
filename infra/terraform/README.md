# Terraform: stockrush on AWS

`terraform apply` builds the demo from nothing; `terraform destroy` removes it and the cost with it.

| Piece | What it is |
|---|---|
| EC2 `t3.small` + Elastic IP | Runs `compose.yaml` plus `compose.aws.yaml`: api, payment-service, PostgreSQL, RabbitMQ, Prometheus, Grafana. It builds the images itself on first boot. No SSH: use SSM Session Manager. |
| S3 (private) + CloudFront | The Angular app. CloudFront also routes the api paths to the instance's port 8080 and `/chaos` to 8081; the security group admits only CloudFront's address range. |
| ACM certificate | HTTPS on your own name (optional). |
| SSM Parameter Store | The JWT secret and the demo admin password, generated by Terraform and read by the instance at boot. |

Rough cost while it runs: the instance is most of it, about US$ 15 a month (`t3.small` on-demand) plus about US$ 2 for 30 GB of gp3 and US$ 4 for the public IPv4 address, around US$ 21 in all; S3 and CloudFront are cents at demo traffic. `terraform destroy` stops all of it.

## First run

You need an AWS account with credentials in the environment (`aws configure` or `AWS_PROFILE`) and Terraform 1.9 or newer.

```bash
cd infra/terraform
terraform init
terraform apply
```

Without `domain_name` the demo answers on the `*.cloudfront.net` address in the `url` output, already over HTTPS.

### With your own name (DNS at Hostinger)

```bash
terraform apply -var domain_name=stockrush.serg-ale.tech -target=aws_acm_certificate.site
terraform output certificate_validation_record
```

In the Hostinger DNS panel add that CNAME (name without the `.serg-ale.tech` suffix). Then run the full `terraform apply -var domain_name=...`: it waits until ACM issues the certificate, then creates the distribution. Last, add a CNAME `stockrush` pointing at `terraform output -raw cloudfront_domain`.

### Putting the app in the bucket

```bash
cd apps/web && npm ci && npx ng build
aws s3 sync dist/stockrush-web/browser "s3://$(terraform -chdir=../../infra/terraform output -raw web_bucket)" --delete
aws cloudfront create-invalidation --distribution-id "$(terraform -chdir=../../infra/terraform output -raw distribution_id)" --paths '/*'
```

Continuous deployment of this step and of the instance is ticket #34.

Sign in as `admin@stockrush.demo` with `terraform output -raw demo_admin_password`. To look at the instance: `aws ssm start-session --target "$(terraform output -raw instance_id)"`; the boot log is `/var/log/stockrush-boot.log`.

## Decisions worth knowing

- **CloudFront to the instance is plain HTTP.** Visitors get HTTPS; the hop from CloudFront to the instance does not, and carries the JWT. The security group limits who can reach it. Fine for a demo; for real data, terminate TLS on the instance.
- **Grafana, Prometheus and RabbitMQ are not reachable from outside.** Use an SSM port-forward to look at them.
- **State is local.** `terraform.tfstate` holds the generated secrets and is git-ignored. A remote backend is the next step if more than one person applies.
- **A new version needs a new instance** (`user_data_replace_on_change`), until CD (#34) exists.

## Why `t3.small`

The free plan refuses `t3.medium` (`The specified instance type is not eligible for Free Tier`). `aws ec2 describe-instance-types --filters Name=free-tier-eligible,Values=true` lists what it accepts. `t3.small` has 2 GiB, so the boot script adds a 2 GiB swap file and `compose.aws.yaml` caps the JVM heaps. If it runs out of memory, set `-var instance_type=c7i-flex.large` (4 GiB): it spends the credits roughly four times faster.

## Things a new AWS account may refuse

- **CloudFront:** a fresh account can answer `Your account must be verified before you can add new CloudFront resources`. It usually clears by itself once the account is fully activated (up to 24 hours); otherwise open an Account and billing case with Support and paste that message. `terraform apply` is safe to repeat: it picks up from what already exists.
- **Instance type:** see above.
